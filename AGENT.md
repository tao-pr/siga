# Guideline for Agent

This project is developed in Rust. It should follow the official structure and convention.

## Generic Project Structure

- Cargo.lock
- Cargo.toml
- src/
 - *.rs
 - main.rs
 - bin/
   - foo-executable.rs
   - multi-executables/
     - foo-executable.rs
     - bar-executable.rs
- tests/
  - some-tests.rs
  - another-tests.rs
  - multi-file-tests
    - main.rs
    - test1.rs


This project structure allows us to conveniently package it into a Cargo package.

- The default executable file is src/main.rs
- The default library file is src/lib.rs

## Coding convention

- Prefer shorter code. Do not write verbose code.
- Prefer shorter function. Max 1-2 sentences of docstring.
- Prefer fewer functions.
- Prefer clear semantic naming of functions, crates, modules, and keep them short.

## Functionalities

The project Siga is an emulator for REST API with rich functionalities including:

- All standard HTTP methods or verbs (see https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Methods)
- JSON request body
- JSON response body
- API swagger spec
- Authentications including JWT, bearer, API key

## Configure an emulated server

The server can be configured simply with swagger file (openapi spec: https://swagger.io/specification/v3.2/). The developer can write YAML or JSON api spec in OpenAPI 3 format, and use it as input for Siga server to emulate.

Siga servers uses the crate 'openapiv3' (https://crates.io/crates/openapiv3) for parsing the swagger api spec file. The crate 'openapi3-parser' is not used because it drops `$ref`, `enum` and `security`.

API spec must define the following
- Path (can be with templating, e.g /api/items/{itemid}, /api/items)
- Request body schema (for verbs that require request body)
- Response body schema (for verbs that return response body)
- $ref can be used if an object is defined for reference somewhere else
- operation object (eg. get, put, post, etc.) must always be defined for all routes
- port must always be defined in the first `servers` URL, e.g. `http://localhost:8080/v1`. Siga uses that port, and serves the paths under the URL path (`/v1`).


## Emulating the server

Siga reads the API spec and opens an API server loop receiving the requests at specified port, path, and HTTP methods. The request will be parsed with the schema defined in the spec, and will return 400 bad request if the request body is not following the request body spec. The response is then generated with random values based on the types of each field:

- Integers: Random integer numbers will be generated (if the min/max criteria is defined in the spec, it will be used)
- String: Random simple english words will be generated
- Enums: A value from the enum will be randomly picked
- Arrays: An array of fixed length (3) will be generated by following the type of each element. If array minItems is defined, minItem will be used. If `uniqueItems` is set to true, each element will also be ensured uniquely generated without duplicates.
- Object (with $ref): The structured object of ref type will be generated. Each field value is generated randomly which also follows the primitive types defined above. 

### NOTE:
- `required` property is not necessary. Siga will fill all fields.
- Free-formed object (https://swagger.io/docs/specification/v3_0/data-models/dictionaries/#free-form-objects) is not supported. Siga will not be able to generate free object without strict schema. If the input Swagger API spec contains a free-form object, it will be rejected.
- Callback is not supported

### Response codes:
- "200" is default response unless user calls the API with extra convention `?force-error={HTTP_CODE}` then the specific HTTP code will be returned.
- Side note, 400 bad request can be naturally emulated by user sending a malformed request which does not comply with the request body spec as discussed in earlier section.

### Authentications / Authorizations

The following authentications are supported by Siga

- apiKey: The fixed API keys are "my-valid-key" to pass authentication, and "my-invalid-key" to fail authentication.
- OAuth2: Authorization can also be configured in the scope. For user to emulate "unauthorized" access, the extra convention `?force-auth=no`. For emulating "authorized" with specified accesses, the extra convention is `?force-auth=read,write,list`. If the forced authorized scopes do not contain the access scopes needed by the API spec of the route that user is calling, Siga will use "401" return code.
